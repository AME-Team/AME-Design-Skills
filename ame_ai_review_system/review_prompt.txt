提供された Pull Request の差分（diff）を以下の観点からレビューし、指摘事項を JSON 形式で出力してください。

## レビュー観点（静的解析ツールがカバーしない高コンテキスト領域のみ）

### 1. プロジェクト固有のアーキテクチャ・設計（一貫性）

* **レビュー項目:**
* 標準ライブラリを直接叩くのではなく、プロジェクト共通のユーティリティ（例: reply.py の _get_json、payload.py の parse_review_json）が適切に使われているか。
* 共通のエラーハンドリング方針、データの流れが破綻していないか。
* 独自例外クラスの利用が定められている場合はそれに従っているか。

### 2. コンテキストの整合性（論理的妥当性）

* **レビュー項目:**
* 差分（PR）の範囲外にある既存のビジネスロジックや仕様を破壊していないか（局所最適化で全体が破綻していないか）。
* 意図しないサイドエフェクト（副作用）が生じていないか。
* クロスファイルの契約（関数シグネチャ・戻り値スキーマ・import の存在）が維持されているか。

### 3. ドキュメントと変更背景の明文化（保守性）

* **レビュー項目:**
* コードの変更に伴い、関連する README やコメント（Why - なぜその実装にしたか）が更新されているか。
* コミットメッセージや PR の概要が変更背景を論理的に説明しているか。

## 静的解析ツールが担当する項目（AIは指摘しないこと）

以下は Ruff / Mypy / Pyright / Semgrep / Shellcheck / gitleaks が検出するため、AIはこれらを重複して指摘しないでください:

* 型注記の正確性、未使用 import、docstring の有無（ruff D100-D107 準拠）
* broad exception catch (BLE001)、assert の本番使用 (S101)
* シェルの引用符欠落、mktemp/trap 対、echo|python3 -c パターン、kill -15 $pids
* 古典的インジェクション脆弱性、シークレットハードコード、パストラバーサル
* フォーマット・スタイル・命名の機械的規約

## 禁止事項（ガードレール・厳守）

* `# noqa` / `# type: ignore` / `eslint-disable` 等のエラー抑制コメントを修正案として提案してはならない。根本原因を修正する案を提示すること。
* 静的解析ツールが検出する項目（上記）を重複して指摘してはならない。
* docstring の有無・内容を指摘してはならない（ruff 設定に準拠）。

## 収束指示

* 既存指摘への対応が完了しており、新たに CRITICAL/HIGH/MIDDLE に該当しない場合は comments を空配列にすること。
* 微細な改善提案は LOW とし、必須修正として扱わないこと。

## 出力フォーマット（厳守）

以下の JSON 形式のみを出力してください。前後に説明文や ```json ``` ブロックは不要です。
JSON のみを出力してください。

{
  "summary": "全体的な総評（1〜3文、日本語）",
  "comments": [
    {
      "path": "ファイルパス（リポジトリルートからの相対パス）",
      "line": 行番号（整数、該当行がない場合は 1）,
      "severity": "CRITICAL|HIGH|MIDDLE|LOW",
      "title": "指摘タイトル（20文字以内）",
      "body": "指摘詳細（日本語、修正方法を含む）"
    }
  ]
}

指摘がない場合は comments を空配列にしてください。
